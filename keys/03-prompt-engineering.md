# Prompt Engineering — Answer Key (1-30)

### 1. What is prompt engineering, and why is it critical for AI applications?
- Идеал: systematic design of inputs to an LLM to reliably steer it toward the desired output.
- Обязательные пункты:
  - LLMs are next-token predictors; the prompt is the main control surface — no retraining needed.
  - Critical because output quality/format depends directly on prompt wording.
  - Combines instructions, examples (few-shot), role, context ordering; cheap vs fine-tuning.
  - Applied iteratively with evaluation.
- Частые ошибки: думать, что одна идеальная фраза всё решит; менять промпты без метрик/тестов.
- Красные флаги: «LLM не зависит от промпта», «промпт-инжиниринг = магия слов».

### 2. Explain zero-shot, one-shot, and few-shot prompting...
- Идеал: различать по числу примеров: zero-shot — модель знает задачу; one-shot — показать формат; few-shot — выучить кастомный паттерн.
- Обязательные пункты:
  - Zero-shot: без примеров, прямая задача (перевод фразы).
  - One-shot: один пример вывода (показать формат, который модель не угадает).
  - Few-shot: несколько примеров паттерна (классификация приоритета бага P0/P2 — свой формат команды).
  - Больше примеров = больше контекста = выше точность для неочевидных задач; растёт стоимость.
- Частые ошибки: давать few-shot, где хватит zero-shot; перегружать контекст.
- Красные флаги: путаница «one-shot = 0 примеров», «few-shot всегда лучше».

### 3. What is chain-of-thought (CoT) prompting, and when should you use it?
- Идеал: попросить модель «думать вслух» — писать шаги рассуждения перед ответом; это повышает точность.
- Обязательные пункты:
  - Модель пишет по одному слову (авторегрессия): записанные шаги становятся контекстом, ответ строится на шагах, а не на угадывании с ходу.
  - Zero-shot CoT: добавить «Let's think step by step». Few-shot CoT: показать решённые примеры с полными рассуждениями.
  - Когда: математика, логика, многошаговые/решения, чтение текста.
  - Не для простых фактов («столица Франции»); reasoning может выглядеть верно, но быть неверным — проверять.
- Частые ошибки: применять к простым задачам; слепо доверять написанным шагам; игнорировать роcт времени/цены.
- Красные флаги: «CoT делает модель умнее», «CoT всегда обязателен».

### 4. Explain self-consistency prompting and how it improves reasoning.
- Идеал: несколько запусков CoT на одном вопросе, финальный ответ = самый консистентный (мажоритарный).
- Обязательные пункты:
  - Разные сэмплы следуют разным путям рассуждений.
  - Правильный ответ «сходится» у многих путей, ошибки единичны → большинство выигрывает.
  - Дешевле/проще чем tree-of-thoughts, надёжнее одного CoT.
  - Улучшает точность на reasoning при цене кратного числа вызовов.
- Частые ошибки: брать один случайный прогон CoT как «самоконсистентность».
- Красные флаги: путать с ансамблем моделей; голосовать по промежуточным шагам вместо финального ответа.

### 5. What is tree-of-thought prompting?
- Идеал: LLM строит дерево рассуждений, оценивает ветки и ищет по ним, а не идёт одной цепью.
- Обязательные пункты:
  - 4 части: разбить проблему на мысли; генератор мыслей (sample/propose); оценщик (value/vote); поиск BFS/DFS с backtracking.
  - Thought — осмысленный средний шаг (уравнение, слово кроссворда); state — проблема + путь.
  - BFS держит b лучших состояний per level; DFS идёт вглубь и откатывается.
  - Game of 24: CoT ~4%, ToT ~74%.
  - Не нужно переобучение; растут cost/latency (десятки вызовов).
- Частые ошибки: использовать для простых задач; терять ветки при неверной оценке.
- Красные флаги: «ToT бесплатен», «ToT = самообучение модели».

### 6. What is ReAct (Reasoning + Acting) prompting, and how does it work?
- Идеал: агент-цикл «Thought → Action → Observation → повтор» до финального ответа — LLM рассуждает и выбирает инструменты.
- Обязательные пункты:
  - Anatomy: LLM + system prompt + tools (имя/описание/схема) + memory + loop controller (бюджет шагов, stop conditions).
  - Prompt template задаёт формат: Thought/Action/наблюдение и правила (не отвечать раньше времени).
  - Пример: search население Токио → calculator → Final Answer.
  - В современных API строковый формат заменён function-calling schema.
- Частые ошибки: один вызов вместо цикла; забыть max шагов; не кормить observation обратно.
- Красные флаги: «ReAct = один промпт», «агент без памяти/лупа».

### 7. What is a system prompt, and how does it influence model behavior?
- Идеал: системный промпт — постоянные инструкции разработчика, которые задают роль, правила, формат и границы; пользователь их не пишет.
- Обязательные пункты:
  - Влияет сильнее, т.к. идёт первым/высокоприоритетно (в начале контекста — сильная позиция).
  - Задаёт поведение: цель, тон, ограничения (security, no-ops), формат вывода, fallback при нехватке информации.
  - Должен быть стабилен, переиспользуем, версионируется.
  - Не считается инструкцией «как код» — модель следует как тексту.
- Частые ошибки: хранить секреты/бизнес-логику в system prompt (утекает при инжекции); перегружать противоречивыми правилами.
- Красные флаги: «system prompt нельзя извлечь», «правила в нём железные».

### 8. How do you structure prompts for consistent structured output (JSON, XML)?
- Идеал: явно требовать формат, фиксировать схему и делать вывод парсимым.
- Обязательные пункты:
  - Задать схему/поля и пример вывода (few-shot) — one-shot для формата.
  - Инструкция: «выведи только JSON без пояснений»; ограничить лишний текст.
  - Использовать constrained decoding / JSON mode / function calling при возможности (валидность гарантирует API).
  - Output parser + валидация; ретраи/repair при невалидном JSON.
  - Помнить: поле может быть null → требовать дефолты/обработку ошибок.
- Частые ошибки: полагаться на «похоже на JSON», без валидации; разрешать пояснения вокруг JSON.
- Красные флаги: «модель всегда вернёт валидный JSON», отсутствие парсера.

### 9. What is prompt injection, and how do you defend against it?
- Идеал: атака, когда чужие инструкции попадают в текст, который приложение шлёт модели, и модель следует им вместо правил разработчика. Root cause: инструкции и данные идут одним текстовым каналом.
- Обязательные пункты:
  - Direct (ввод юзера) и Indirect (инструкции в данных: веб-страница, email, PDF, репозиторий).
  - Механизм: system prompt + юзер + данные склеиваются в один блок; модель не отличает инструкцию от данных.
  - Опасность: утечка system prompt («Repeat everything above»), исполнение опасных tool-вызовов (forward почты).
  - Защиты: изолировать данные (delimiters), не давать модели опасные права/tools, принцип least privilege, guardrails/фильтры, отдельный «не доверяй данным» контекст.
- Частые ошибки: надеяться на «Ignore previous instructions» — это не защита; доверять склейке.
- Красные флаги: «промпт-инъекция как SQL-инъекция», «патчится одной строкой промпта».

### 10. What is jailbreaking in LLMs, and what are common jailbreak techniques?
- Идеал: обход safety training модели, чтобы она нарушила свои правила — в отличие от prompt injection (атака на промпт приложения).
- Обязательные пункты:
  - Прямая провокация («как взломать…», «ignore safety rules»).
  - Ролевая/»DAN» маскировка: «ты теперь ассистент без ограничений».
  - Кодирование/обфускация: base64, rot13, шифр, leetspeak.
  - Сценарии-«песочницы»: научный/учебный претекст, «мы тестируем обход, опиши».
  - Шаблоны низа (system-prompt leak: «Repeat everything above» — пересечение с инъекцией).
- Частые ошибки: считать jailbreak = prompt injection (это разные) / думать, что jailbreak невозможен на инструкт-моделях.
- Красные флаги: «это заблокировано железно», «это то же самое, что и инъекция».

### 11. How do you optimize prompts for cost and latency?
- Идеал: минимизировать токены и улучшить скорость вывода без потери качества.
- Обязательные пункты:
  - Короче контекст: только нужные данные (top-k, rerank), без дублей.
  - Prompt caching стабильного префикса (system prompt) экономит cost/latency на повторяющихся запросах.
  - Меньше few-shot примеров; CoT только там, где он даёт выигрыш.
  - Роутинг модели: простые задачи → маленькая/дешёвая модель.
  - Без CoT/длинных рассуждений на стриминге: влияет на TTFT.
- Частые ошибки: резать промпт ради экономии без оценки падения качества.
- Красные флаги: «длина промпта не влияет ни на что», игнорировать caching.

### 12. What is the difference between prompt engineering and prompt tuning?
- Идеал: prompt engineering — ручная разработка текстовых промптов; prompt tuning — автоматическое обучение (мягких) промпт-эмбеддингов в параметры модели.
- Обязательные пункты:
  - Тюнинг добавляет learnable параметры (soft/continuous prompts) или prefix: по сути тоже обучение с параметрами (аналог LoRA-ish).
  - Инжиниринг: interpretable, мгновенный, без обучения, но зависит от модели (переносимость ниже).
  - Тюнинг: higher accuracy, дорого, требует доступа к градиентам/данным.
  - Промежуточное: API fine-tuning vs prompt tuning разница — контекстный промпт vs веса/эмбеддинги.
- Частые ошибки: путать prompt tuning с fine-tuning весов (это разные механики).
- Красные флаги: «prompt tuning = длина промпта», «это одно и то же с RAG».

### 13. What is a prompt template, and how do you design one for production use?
- Идеал: многоразовый шаблон-скелет с placeholder'ами и структурированными полями, который приложение заполняет перед вызовом.
- Обязательные пункты:
  - Фиксированные блоки: system role/правила, инструкция, контекст/данные (якорь для инъекции), вопрос/задача, формат вывода.
  - Versioning, дефолты, валидация обязательных полей; NDJSON/строгая схема для генерации.
  - Почему: consistency, переиспользование, тестируемость, лёгкий A/B, удержание промпт-кэша.
  - Избегать раздувания/дублирования; экранировать user-ввод.
- Частые ошибки: шаблон без слотов для пользовательского ввода (всё в одном тексте); несоответствие примеров реальному входу.
- Красные флаги: «шаблон = просто f-string», пренебрежение валидацией слотов.

### 14. How do you handle multi-turn conversations with LLMs?
- Идеал: хранить историю сообщений (system+user+assistant) и корректно передавать её в каждый следующий вызов, управляя ограничением контекста.
- Обязательные пункты:
  - Message-роли: system/user/assistant (+tool) — модель видит всю историю.
  - Ограничение окна: обрезка/суммаризация старой истории (context compaction) при длинных диалогах.
  - Сохранять ключевые факты/намерения (структурированная память), не только текстовый лог.
  - Потоковые ответы + состояния (state) для агентных диалогов; guards на длину.
  - Учитывать lost-in-the-middle: ранние правила теряют силу в длинной истории.
- Частые ошибки: передавать всю историю без ограничений → дорого/проблемы; потеря контекста.
- Красные флаги: «история не нужна, llm помнит сама», бесконечное накопление токенов.

### 15. What is role prompting, and when is it effective?
- Идеал: задание модели роли/персоны для стабилизации поведения, тона и границ.
- Обязательные пункты:
  - «You are an expert…» → задаёт рамки знаний, тон, приоритеты.
  - Эффективен: стиль (клон-копирайтер), экспертиза (юрист итд), ограничение scope.
  - Не является железной защитой/качеством — роль не заменяет инструкций; LLM всё равно последует неоправданной просьбе.
  - Слаб на задачах, где нужна точность, но помогает на открытых/креативных.
- Частые ошибки: думать, что роль = магическая гарантия знаний или безопасности.
- Красные флаги: «роль сделает модель гениальной», путать роль с system-prompt security.

### 16. What is prompt chaining, and how do you design a chain of prompts for complex tasks?
- Идеал: разбить задачу на последовательность маленьких промптов, где выход предыдущего = вход следующего (не путать с CoT).
- Обязательные пункты:
  - Зачем: каждый шаг прост → точнее, ошибки локализуются, шаги переиспользуются.
  - Паттерны: straight chain; extract-then-act; generate-then-check (рефлексия).
  - Пример: статья → summary → соцпост → хэштеги.
  - Дизайн: короткие шаги, передавать только нужное, валидировать промежуточный вывод.
  - Цена: N вызовов = рост стоимости/латентности; ошибки каскадируются.
- Частые ошибки: путать с CoT; длинные цепочки без проверок.
- Красные флаги: «выход шага всегда корректен», игнорировать стоимость.

### 17. How do you evaluate and iterate on prompt quality?
- Идеал: зафиксировать метрики и тестовый корпус, сравнивать версии промптов — итеративно улучшать.
- Обязательные пункты:
  - Golden set с ожидаемыми ответами для измерения качества.
  - Метрики: accuracy/формат/отсутствие халлуцинаций; human eval + LLM-as-judge.
  - A/B разных промптов на одних данных; версионирование.
  - Робастность: вариации формулировок не должны менять ответ (sensitivity).
  - Регресс-тесты: новые изменения не ломают прошлые кейсы.
- Частые ошибки: оценивать промпты вручную на 2-3 примерах, без датасета.
- Красные флаги: «промпт хорош, если один раз сработал», нет счётчиков качества.

### 18. What are meta-prompts, and how can they be used to generate prompts?
- Идеал: промпты о промптах — инструкции модели написать/улучшить/скомпоновать другой промпт.
- Обязательные пункты:
  - Использование: генерация системы-промпта под задачу, рефакторинг, усиление ясности.
  - Пример: «составь system prompt для классификации отзывов с правилами и примерами».
  - Мета-уровень: итеративно (напиши → проверь → улучши) — как рефлексия.
  - Полезно при дизайне промптов для новых задач, но требует валидации результата.
- Частые ошибки: слепо использовать сгенерированный промпт без тестов.
- Красные флаги: «мета-промпт всегда оптимален», «это обучение модели» (нет — это текст).

### 19. What are the common failure modes in prompting, and how do you debug them?
- Идеал: систематический дебаг по категориям сбоев.
- Обязательные пункты:
  - Формат/невалидный JSON; нехватка/игнор данных (lost-in-the-middle); халлуцинации; лишний текст.
  - Плохая формулировка (неоднозначность), конфликт правил, переобучение на few-shot.
  - Debug-подход: воспроизвести, изолировать (задать один вопрос), менять переменную, тестить версии, логировать вывод.
  - Инструменты: unit-тесты на промпт, эхокейсы, golden set.
- Частые ошибки: менять всё сразу, не изолируя причину; винить модель без проверки промпта.
- Красные флаги: «сбой всегда из-за data», «промпт ни при чём».

### 20. How do you handle edge cases and adversarial inputs in prompt design?
- Идеал: тестировать на крайних входах и проектировать устойчивость заранее.
- Обязательные пункты:
  - Edge: пустой/огромный ввод, юникод, инъекции, конфликт с данными.
  - Валидация/санитизация ввода; ограничение ролей и инструментов (least privilege).
  - Defensive промпты: разделять данные и инструкции; не доверять данным.
  - Автотесты на adversarial кейсы в eval-наборе; мониторинг.
- Частые ошибки: тестировать только happy path; надеяться на prompt-строку как защиту.
- Красные флаги: «мы обработаем после», пренебрежение правами инструментов.

### 21. What is the "lost in the middle" problem in long-context prompting?
- Идеал: деградация использования информации из середины длинного контекста — края (начало/конец) используются лучше (U-shaped curve).
- Обязательные пункты:
  - Причины: attention растягивается тонко; позиционные смещения (близость к концу ответа); привычка к human-тексту «выводы по краям»; непрактика полной длины.
  - Контекстное окно = вместимость, а не гарантия качества — провал в середине «тихий» (нет ошибки, есть уверенный неверный ответ).
  - Фиксы: посылать меньше, но релевантного (реранкер: top-k); при многочunks — упорядочить: самые важные в начале/конце, вопрос в самом конце повторять критичные инструкции по краям; map-reduce по чанкам; сначала extract, потом отвечать; выбор модели по тесту Needle-in-a-Haystack.
- Частые ошибки: считать, что большой контекст решает всё; обвинять ретривер при отличном retrieval.
- Красные флаги: «Если поместилось, модель всё прочитает», путать с обрезанием текста.

### 22. What are output parsers, and why are they needed for production applications?
- Идеал: код, который извлекает и валидирует структурированные данные из произвольного вывода LLM — надёжный мост между текстовым выводом и логикой/схемой приложения.
- Обязательные пункты:
  - Зачем: модель возвращает текст → парсить JSON/tool-calls; гарантия формата контракта.
  - Виды: JSON/структурные парсеры, constrained decoding/JSON mode, schema-валидация, repair/re-prompt при невалидном выводе.
  - Интеграция: prompt, парсинг, fallback, ошибки парсинга обрабатываются кодом (не выброс).
  - Влияет на: интеграция с бизнес-логикой, снижение хрупкости (форматные сбои).
- Частые ошибки: извлекать регулярками по «обёрткам», без валидации схемы.
- Красные флаги: «модель выдаёт валидный вывод всегда», парсер без обработки сбоев.
### 23. How do you handle multi-language prompting effectively?
- Идеал: адаптировать промпты под целевые языки и тестировать на них, а не полагаться на английский.
- Обязательные пункты:
  - Переводить/адаптировать инструкции и few-shot примеры; не смешивать языки.
  - Выбирать мультиязычную модель; следить за токенизацией целевого языка.
  - Оценивать на мультиязычном eval-набоpe, а не только качество перевода.
  - Учитывать форматы (даты/числа) и локаль.
- Частые ошибки: дословный перевод; считать, что англ. промпт «работает везде».
- Красные флаги: «промпт переводить не надо», нет мультиязычных eval.

### 24. Your few-shot prompting gives inconsistent results across similar inputs. How do you stabilize it?
- Идеал: найти источник вариабельности и сделать вывод детерминированным/стабильным.
- Обязательные пункты:
  - Проверить few-shot примеры: они должны быть однородны по формату и типам входов (диверсифицировать по краевым случаям).
  - Снизить temperature/top-p при детерминированных задачах; seed где поддерживается.
  - Зафиксировать формат вывода (схема) и заставить выводить только его.
  - Убедиться в балансе классов в примерах; проверить неоднозначность входов.
  - Regression тесты на золотом наборе; логировать расхождения.
- Частые ошибки: менять примеры вручную без измерения; считать temperature единственной причиной (это часто шаблон/классовая предвзятость).
- Красные флаги: «просто поставь temperature=0 и всё стабильно» — без eval по-прежнему риск; игнор формата.

### 25. Your LLM classification system is too sensitive to prompt wording changes. How do you reduce prompt sensitivity?
- Идеал: сделать классификатор устойчивым к тем же формулировкам входа и к изменениям UX/промптов.
- Обязательные пункты:
  - Нормализовать/чистить вход (token, регистр, стоп-слова где уместно) — снизить вариативность.
  - Зафиксировать стабильный заголовок/формат; избегать вольных парафразов инструкций.
  - Строгая инструкция: при неоднозначности → выдать дефолт/направление, а не случайность.
  - Одинаковый few-shot по формату и порядку; test с перестановками примеров.
  - Замерять робастность (перефразировать те же кейсы) и сравнивать версии на золотом наборе.
- Частые ошибки: искать «простое слово» вместо системного решения; игнорировать класс-дисбаланс.
- Красные флаги: «модель нестабильна из-за одной фразы — поменяем строку», нет робастного eval.

### 26. Your chatbot's system prompt containing proprietary business logic is being leaked by users. How do you prevent it?
- Идеал: считать system prompt потенциально извлекаемым и строить защиту без зависимости от «не разглашай».
- Обязательные пункты:
  - Не хранить секреты/ключи/полную бизнес-логику в промпте — выносить в код/рантайм (важные решения в приложении, не в строке).
  - Разделять доверенный контекст от пользовательского; ограничить tools и их права (least privilege).
  - Prompt hardening: инструкция не раскрывать, но это не гарантия — защита в архитектуре.
  - Guardrails/фильтры на выводе (детекция слива), мониторинг/логирование попыток.
  - Allowlist/denylist ответов; fallback-шаблон.
- Частые ошибки: полагаться только на «Never reveal…», считать промпт секретом.
- Красные флаги: «системный промпт нельзя украсть», хранение ключей в промпте.

### 27. Your LLM agent is vulnerable to prompt injection that reveals the system prompt. How do you defend it?
- Идеал: защитить агента в глубину — от кражи инструкций и от выполнения враждебных tool-команд.
- Обязательные пункты:
  - Не доверять содержимому данных (web/email/Docs) как инструкциям: размечать/изолировать инпут от инструкций.
  - Ограничение прав: агент не может сделать опасные действия без подтверждения (human-in-the-loop, подтверждение для отправки/удаления/перевода денег).
  - Меньше «лобовых» промптов: не вставлять весь контент в промпт, использовать отдельные каналы/инструменты; проверять намерение.
  - Guardrails: фильтры на вывод/действия, алерты на повторы/обфускации, logging.
  - Sanitize входа: отбрасывать «инструкции» (спецфразы) из данных, но помнить: полное решение — знание-контроль + права, а не одна строка.
- Частые ошибки: требовать от модели «просто не следовать данным», давать агенту слишком широкие права.
- Красные флаги: «проблема решена промптом», агент имеет полный доступ к критичным действиям.

### 28. Your chain-of-thought prompting is not improving LLM accuracy on reasoning tasks. What do you fix?
- Идеал: CoT не работает если шаги ложные/сбивающие, примеры нерепрезентативны или задача не требует рассуждений.
- Обязательные пункты:
  - Убедиться, что задача действительно многошаговая (math/logic) — не просто фактовопрос.
  - Few-shot CoT: примеры должны покрывать все типы ошибок и краевые случаи; проверять их корректность.
  - Zero-shot CoT: использовать «Let's think step by step» или «think step by step explicitly» для конкретной модели.
  - Проверить, не даёт ли модель шаги, выглядящие правильно, но ведущие к неверному ответу; исправить логику в примерах.
  - Рассмотреть self-consistency (несколько путей), tree-of-thoughts (когда один неверный первый шаг ломает всё) или fine-tuning на reasoning-данных.
  - Измерить: замерить accuracy до/после изменений на held-out наборе.
- Частые ошибки: добавлять больше текста без смены модели/примеров; не тестировать.
- Красные флаги: «CoT всегда улучшает», «добавим побольше шагов» без eval.

### 29. Your AI system works in English but fails for other languages. How do you add multilingual support?
- Идеал: адаптировать и тестировать на каждом языке, а не просто переводить промпт.
- Обязательные пункты:
  - Few-shot примеры на целевом языке; инструкции адаптировать, а не дословно.
  - Выбрать модель с хорошей многоязычной поддержкой; проверить tokenizer (не все токенизируют кириллицу/арабицу одинаково).
  - Нормализовать вход (unicode, date formats) и формат вывода.
  - Eval: золотой набор на каждом языке; метрики релевантные.
  - Учитывать RTL языки (арабский), тон/культуру; не просто перевод слов.
- Частые ошибки: переводить промпт машинным переводом и считать, что готово; полагаться на «модель знает все языки».
- Красные флаги: «достаточно английских примеров», нет мультиязычного eval.

### 30. Your zero-shot cross-lingual transfer from English fails on other languages. How do you fix it?
- Идеал: не полагаться на zero-shot кросс-лингвальную передачу — использовать целевой язык.
- Обязательные пункты:
  - Zero-shot с английским работал, потому что модель сильнее на EN; на целевом языке нужны примеры (few-shot) или языково-специфичный промпт.
  - Few-shot + few-shot на целевом языке; переводить примеры (с проверкой) — не идеально, но работает.
  - Prompt chaining: определить язык → использовать релевантные примеры/контекст.
  - Рассмотреть fine-tuning на параллельных данных или multilingual model.
  - Тестировать на реальных данных целевого языка (не на переведённых).
- Частые ошибки: думать, что zero-shot = языконезависимо; просто переключить ввод на целевой язык без подготовки.
- Красные флаги: «модель multilingual, значит zero-shot работает», игнорировать лингвистические различия.
