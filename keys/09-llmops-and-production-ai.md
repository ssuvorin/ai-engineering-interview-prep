# LLMOps and Production AI — Answer Key (1-27)

### 1. How does Prompt Caching work?
- Идеал: стабильный префикс промпта кэшируется в KV-кеш; следующий запрос с тем же началом загружает кэш вместо повторного вычисления.
- Обязательные пункты:
  - KV-кеш строится в prefill-фазе; cache-write стоит ~1.25x нормальной цены, cache-read ~0.1x — экономия ~90%.
  - Prefix-правило: кэш работает только если начало идентично посимвольно; одна меняющаяся строка (дата/user-id) в начале ломает весь кэш.
  - TTL по умолчанию 5 минут (опция 1 час); длинный TTL чуть дороже, но больше хитов.
  - Кэшировать: system instructions, большие документы, tool definitions, few-shot примеры; вопрос — в конце, не кэшируется.
- Частые ошибки: класть динамику (сегодняшняя дата) в начало промпта; не проверять cache-read в ответе.
- Красные флаги: «prompt caching = semantic caching» (переиспользует финальный ответ), «кэш бесплатный для всех запросов» (запись дороже).

### 2. Prefill vs Decode
- Идеал: prefill читает весь промпт одним параллельным проходом и выдаёт первый токен; decode генерирует остальные токены по одному, переиспользуя KV-кеш.
- Обязательные пункты:
  - Prefill: параллельно обрабатывает все входные токены (matrix×matrix), пишет KV-кеш, выводит первый токен.
  - Decode: autoregressive, один токен за шаг; matrix×vector; читает и расширяет KV-кеш на каждом шаге.
  - KV-кеш — мост: без него каждый decode-шаг пересчитывал бы все прошлые ключи/значения — полная работа ~O(n²).
  - Фазы зеркальны: prefill (compute, высокая утилизация) vs decode (memory-bound, низкая утилизация).
- Частые ошибки: думать что decode производит всё сразу; путать порядок написания токенов.
- Красные флаги: «prefill и decode — разные модели/веса», «decode выдаёт целый ответ за раз».

### 3. Why is prefill compute-bound and decode memory-bandwidth-bound?
- Идеал: prefill делает тяжёлое матричное умножение по всем токенам сразу, поэтому упирается в скорость вычислений; decode делает крошечное умножение на один токен, но при каждом шаге считывает все веса + растущий KV-кеш, поэтому упирается в скорость переноса данных.
- Обязательные пункты:
  - Prefill: matrix×matrix, все токены параллельно → compute units ~90%+ busy.
  - Decode: matrix×vector на один токен; на каждый шаг читается вся модель (гигабайты весов) + весь KV-кеш → math units ~20-40% busy.
  - Attention-часть prefill растёт квадратично с длиной промпта.
  - TTFT от prefill; TPOT от decode; decode обычно занимает большинство времени ответа.
- Частые ошибки: считать обе фазы compute-bound; не учитывать чтение весов в decode.
- Красные флаги: «decode ограничен math», «prefill ограничен памятью».

### 4. What is chunked prefill, and why does it improve tail latency under mixed traffic?
- Идеал: длинный prefill разбивается на маленькие куски, которые вставляются между decode-шагами в батч; ни один пользователь не ждёт целого длинного prefill.
- Обязательные пункты:
  - Проблема co-located serving: один запрос с длинным промптом (например 10k токенов) стопит decode всех остальных в батче на ~1 секунду → tail latency spike (generation stall/interference).
  - Chunked prefill: разбить prefill на небольшие чанки, каждому decode-шагу добавить небольшую порцию prefill; ни один запрос не блокирует decode надолго.
  - Trade-off: TPOT чуть растёт у всех (каждый decode-шаг несёт лишний prefill), TTFT чуть растёт (prefill идёт кусками) — боль «размазывается», а не удаляется.
  - Chunked prefill и prefill-decode disaggregation — разные вещи: первое смягчает interference на одном GPU, второе убирает её разделением железа.
- Частые ошибки: считать chunked prefill полным устранением interference; не замечать рост TPOT.
- Красные флаги: «chunked prefill = disaggregation», «после него все метрики строго лучше».

### 5. What is Prefill-Decode Disaggregation, and when does it pay off?
- Идеал: prefill и decode выполняются на отдельных GPU; router ведёт запрос, prefill-worker строит KV-кеш и выдаёт первый токен, KV-кеш передаётся по быстрой сети в decode-worker, который генерирует остальное без помех.
- Обязательные пункты:
  - 4 части: router, prefill workers (compute-heavy, tuned для чтения промптов), decode workers (memory-heavy, tune для обслуживания многих пользователей), KV-кеш transfer (NVLink/InfiniBand/RDMA).
  - Prefill и decode не делят один GPU → нет generation stall/interference; оба показателя (TTFT и TPOT) настраиваются независимо.
  - Независимое масштабирование: длинные промпты → больше prefill-в; длинные ответы → больше decode-в.
  - Оплата окупается при высокой доле смешанных запросов и строгих SLO на обоих метриках; нужно fast interconnect, иначе transfer съедает выигрыш.
  - Не платит при малом масштабе, коротких промптах, слабой сети.
- Частые ошибки: забыть router; не учитывать latency передачи KV-кеша (2 GB = ~20-50ms).
- Красные флаги: «disaggregation бесплатна», «не нужен interconnect», устанавливать на каждую мелкую систему.

### 6. Explain the AI product lifecycle from ideation to production.
- Идеал: конвейер от идеи до продакшена итеративный: идея → прототип → eval → разработка → деплой → мониторинг → улучшение.
- Обязательные пункты:
  - Определить бизнес-проблему, пользователя и метрики успеха ДО написания кода.
  - Proof of concept: быстрая проверка, что LLM может решить задачу (промпт, few-shot), до инвестиций в инфраструктуру.
  - Итерация промптов + сбор evaluation-датасета (реальные сценарии, краевые случаи).
  - Выбор стека: RAG/agent/orchestration, модель (коммерческая API vs self-hosted), кэширование, guardrails.
  - Offline evaluation (benchmarks) + online (A/B, canary, метрики качества продуктива).
  - Мониторинг и обратная связь: замеры качества, cost, latency; ретраи, fallback-стратегии.
  - После релиза — цикл: собираем данные → исправляем промпты → A/B → релиз.
- Частые ошибки: пропускать eval; деплоить непроверенный промпт; нет отката/фолбэка.
- Красные флаги: «lifecycle = запустить и забыть», нет фазы измерения качества.

### 7. What is LLMOps, and how does it differ from traditional MLOps?
- Идеал: LLMOps — операционные практики для LLM-приложений: управление промптами, RAG/agents, model serving, cost/latency, observability; MLOps фокусируется на ML-моделях (данные, обучение, версии весов).
- Обязательные пункты:
  - Основной артефакт LLMOps — промпт/система промптов и контекст, а не веса модели; инференс-центричность вместо training-центричности.
  - Управляют: versioning промптов, retrieval pipelines, tool/function definitions, agent loops, guardrails, hallucination/quality.
  - Serving: vLLM/TGI/SGLang/TensorRT-LLM, continuous batching, quantization, disaggregation.
  - Observability: не только CPU/memory/latency, но и токены, cost per request, cache hit rate, качество ответов.
  - MLOps: data pipelines, feature stores, experiment tracking, model registry, CI/CD для моделей; LLMOps добавил слой LLM-специфики.
- Частые ошибки: говорить «это обычный MLOps» без слоя промптов/качества.
- Красные флаги: «LLMOps = MLOps без изменений», «нужно только следить за latency».

### 8. How do you serve LLMs in production?
- Идеал: высокопроизводительный serving engine с эффективным KV-кеш управлением и батчингом (vLLM PagedAttention + continuous batching), OpenAI-совместимым API, горизонтальным масштабированием.
- Обязательные пункты:
  - PagedAttention: KV-кеш в фиксированных блоках (фикс. число токенов), выделение on-demand — нет over-reservation, почти нет fragmentation.
  - Sharing: идентичные префиксы (system prompt) хранятся один раз, блоки шарингуются между запросами.
  - Continuous batching: finished request выгружается, новый берётся в тот же decode-шаг; GPU всегда занят.
  - OpenAI-совместимый endpoint: /v1/chat/completions, легко переподключить клиент.
  - Масштабирование: множество реплик за load balancer; одним vLLM на одном GPU можно обслужить много пользователей.
- Частые ошибки: деплоить без батчинга; не управлять kv-cache и длиной контекста.
- Красные флаги: «serving = предсказание модели в цикле без движка», «одна реплика», «наивный static batching».

### 9. What is model quantization?
- Идеал: хранение/вычисления весов и активаций модели в меньшей точности (FP32→INT8/INT4) для экономии памяти и ускорения без существенной потери качества.
- Обязательные пункты:
  - FP32 (32 бита/4 байта) → INT8 (1 байт, 256 значений) 4x меньше, → INT4 (0.5 байта, 16 значений) 8x меньше.
  - Пример: 7B модель в FP32 ≈ 28 GB; INT8 ≈ 7 GB; INT4 ≈ 3.5 GB — помещается на один GPU/ноутбук.
  - Core mechanic: scale + zero-point переводят real range → целые; округление = потеря качества.
  - Symmetric (zero-point=0, fast) vs Asymmetric (для односторонних данных); per-tensor vs per-channel (сохраняет детали).
  - Weight-only (обычно для LLM, безопаснее) vs weight+activation (быстрее, но outlier-проблема у активаций).
  - Методы: GPTQ (layer-by-layer с коррекцией), AWQ (activation-aware, защищает важные веса), bitsandbytes (лёгкое 4/8bit-loading), GGUF+llama.cpp (CPU).
- Частые ошибки: квантизировать активации игнорируя outliers; не проверять качество после.
- Красные флаги: «квантизация бесплатна», «INT4 идентично FP32».

### 10. Explain post-training quantization (PTQ) vs quantization-aware training (QAT). What breaks when you push weights to 2-4 bits?
- Идеал: PTQ — дешёвая квантизация уже обученной модели калибровкой scale/zero-point; QAT — обучение с симуляцией округлений, чтобы веса выдержали низкую точность.
- Обязательные пункты:
  - PTQ: «train first, shrink later»; нужен лишь небольшой калибровочный датасет; популярно и легко; точность страдает на INT4.
  - QAT: «train so it is ready»; симулирует rounding во время обучения, модель подстраивает веса; лучшая точность на низких битностей, требует полного обучения.
  - При 2-4 бита ломается многое: значение на шаг становится грубым; outlier весов/активаций уже сложно уместить в 16/256 состояний; накапливается loss.
  - GPTQ: после округления веса корректирует остальные — сохраняет качество на 4 бита.
  - AWQ: определяет важные веса по большим активациям и защищает их.
  - 2-бита: заметные ошибки; INT4 обычно sweet spot.
- Частые ошибки: заявлять PTQ при 2 бита без защиты outliers; путать QAT с fine-tuning.
- Красные флаги: «2-бита бесплатно», «QAT не нужен, PTQ везде работает».

### 11. How do you monitor LLM applications in production?
- Идеал: сквозной мониторинг 3 pillars (traces, metrics, logs) + специфичные для LLM: качество ответов, токены/стоимость, guardrails, rate limits.
- Обязательные пункты:
  - Лаг: TTFT, TPOT, end-to-end, p95/p99; стабильность под нагрузкой.
  - Throughput: tokens/sec, requests/sec, GPU utilization, batch size.
  - Cost: cost/token (input/output), total monthly spend, прогноз бюджета.
  - Качество: eval-метрики, hallucination rate, refusal rate, настроение фидбека (likes/dislikes), экспертные/вовлечённых.
  - Алерты: превышение порогов latency, cost, error rate, деградация качества.
  - Инструменты: Prometheus+Grafana, LangSmith, Phoenix, Weights&Biases, Helicone, Datadog.
  - Правило: предупреждать о деградации качества, а не только о падении сервиса.
- Частые ошибки: мониторить только инфраструктуру (CPU/RAM), не смотреть качество.
- Красные флаги: «мониторинг = uptime», «токен-стоимость не считаем».

### 12. What is LLM observability?
- Идеал: полная видимость внутренних шагов LLM/агента: трассы и спаны (trace = весь запрос; span = один шаг), логи, метрики; чтобы видеть почему модель так ответила.
- Обязательные пункты:
  - Проблема: агент недетерминированный — один input → разные пути; ошибки могут быть тихими (выглядит корректно, но неверно).
  - Ключевое: трассировка решает «почему так» — видно цепочку решений и tool calls.
  - Logs: текстовые записи о событиях (вход/выход, tool calls).
  - Metrics: aggregated числа (tokens, cost, latency) за интервалы времени.
  - Traces: journey одного запроса через все шаги (query, prompt, model, tools, final), с spans и вложенностью.
  - Для agent'ов критично: почему, что стоп-условие, где потерялись деньги (price/tokens).
  - Соблюдать: не логировать prompt целиком, а логировать структурированно (inputs/outputs, parent spans).
- Частые ошибки: путать observability с логированием (которое не даёт трасс); не логировать tool результаты.
- Красные флаги: «агент наблюдаем по интуиции», «нет трассировки».

### 13. What are guardrails for LLMs, and how do you implement them?
- Идеал: guardrail = проверки на входе и выходе, чтобы не допустить небезопасный/не офф-топик контент; включая input и output guard.
- Обязательные пункты:
  - Входной guardrail: блокирует вредный запрос до того, как main LLM его увидит.
  - Выходной guardrail: фильтрует ответ перед выдачей пользователю.
  - Техники: от простых banned-word/patterns до guard model — второго (обычно малого) LLM, возвращающего «safe/unsafe» по смыслу, а не по точным словам.
  - Guardrails лежат вокруг модели, не в ней: поведение контролируется.
  - Типы: topic, safety, privacy, format, factual.
  - Правило: ставить и input, и output guardrail, а не только один.
- Частые ошибки: считать guardrail единственным фильтром; полагаться только на system prompt.
- Красные флаги: «guardrail = промпт», «блокировок не бывает».

### 14. How do you implement content filtering for AI outputs?
- Идеал: слой фильтрации над выходом модели, который убирает недопустимый контент до показа пользователю.
- Обязательные пункты:
  - Входные фильтры (запрещённые слова) — быстрые, но обходимы (h a c k, перефразировки); выходные фильтры (шаблоны PII: re.sub(r'\d{10}', '[hidden]', answer)).
  - Два места: перед моделью (input) и после (output); и то и другое используется.
  - Guard model — второй/небольшой LLM оценивает безопасность входного и выходного (safe/unsafe), может работать на уровне смысла.
  - Политики на уровне текста: блокировка harmful content, PII (карты, телефоны, email), приватные данные, запрещённые темы.
  - Логировать блокировки для непрерывного улучшения; тесты на good/bad сообщения.
  - Фолбэк: при срабатывании фильтра вернуть вежливый отказ / безопасный шаблон.
- Частые ошибки: фильтровать только вход или только выход; полагаться на один метод.
- Красные флаги: «content filter = один слой регексов», «не фильтровать выход».

### 15. How do you estimate the cost of running an AI-powered feature in production?
- Идеал: модель затрат на основе токенов на запрос × запросы в день, с учётом контекста, промпт-кэша, latency и serving infra.
- Обязательные пункты:
  - Формула по API: cost = (input_tokens×price_in + output_tokens×price_out) × requests; считать чтение длинных контекстов и кэш.
  - Компоненты: токены в промпте (с контекстом, few-shot), токены в ответе; overhead RAG/документов в промпте.
  - Модели: цены за 1K/1M токенов input/output у провайдера; обычно output дороже.
  - Снижение: prompt caching (cost/re-read), роутинг на дешёвые модели для простых задач.
  - Self-hosted: GPU hours, память (kv-cache, диск), электричество, амортизация железа.
  - Мониторинг реальной стоимости против прогноза.
- Частые ошибки: забыть про output-токены, про длиный системный промпт, про ретраи.
- Красные флаги: «расчёт только input», «не считаем кэш-хиты».

### 16. How do you optimize LLM inference costs in production?
- Идеал: комбинация техник на уровне serving и запросов: batching, KV-кэш менеджмент, квантизация, роутинг, кэширование промптов.
- Обязательные пункты:
  - На уровне serving: continuous batching + paged attention (vLLM) повышают throughput на GPU → ниже стоимость за токен.
  - Промпт-кэширование (prefix caching) — дешёвое повторное чтение стабильного начала промпта.
  - Квантизация/оптимизация модели (INT8/INT4) — меньше VRAM, дешевле оборудование.
  - Model routing: для простых задач маленькая дешёвая модель, для сложных — крупная.
  - Context engineering: уменьшить промпт до нужного (RAG top-k, обрезка длинного хвоста контекста).
  - Speculative decoding / сжатие ответа — меньше сгенерированных токенов.
  - Мониторинг стоимости в реальном времени, алерты при пике.
- Частые ошибки: рубить качество ради токен-экономии без метрик.
- Красные флаги: «только Батчинг», «квантизация всё решает», «cost = чёрный ящик».

### 17. How do you implement A/B testing for LLM systems?
- Идеал: сравнение двух конфигураций (модель, промпт, параметры) на реальных пользователях, с метриками качества и бизнес-метриками.
- Обязательные пункты:
  - Разделение трафика: стабильный hash по user/request-id (не по каждому запросу, чтобы держать user-experience консистентной).
  - Параметры сравнения: model version, prompt version, temperature, max tokens, RAG config, granularity.
  - Метрики: бизнес-метрики (конверсия, retention) + quality eval (автоматический judge, ручная оценка, фидбек-лайки).
  - Меньше шума: одинаковые входы для сравнения (golden dataset); сокращение трафика до статистической значимости; контроль сегментами.
  - Продолжительность: достаточно данных для значимости; не бесконечно.
  - Rollout: canary-деплой, A/B контроль, откат.
  - Соблюдать: не отправлять фабрикованные ответы — реальные пользователи.
- Частые ошибки: сравнивать по одному прогону; не учитывать персистентность сессии.
- Красные флаги: «A/B на случайном%», «плавающая статистика».

### 18. What is CI/CD for AI applications, and how does it differ from traditional CI/CD?
- Идеал: автоматизация тестирования и деплоя, включая модель/промпты/контекст, с регрессией качества.
- Обязательные пункты:
  - CI для ML: тесты на данных + пайплайн обучения/инференса единиц качества; артефакт — не только код, но и веса/промпты.
  - CD: автоматическая публикация (model registry, prompt registry), деплой на инференс-платформу.
  - Отличие: недетерминированность → нужны eval-тесты и gold sets; неуспех может быть «модель отвечает, но плохо».
  - Обычный CI/CD тестирует функции/код; для LLM дополнительно идёт тест качества ответов (LLM-judge, goldens).
  -   - Pipeline: build → квантизация/оптимизация → unit/integration e2e tests → deploy → canary → мониторинг; главное отличие — eval моделей и качественные тесты ответов.
- Частые ошибки: деплоить модель без eval; путать CI код vs CI/LLM.
- Красные флаги: «CI/CD для обычного софта полностью подходит для LLM».

### 19. How do you version and manage prompts in production?
- Идеал: промпты хранить как код/артефакт, версионировать, тестировать, A/B-тестировать и откатывать.
- Обязательные пункты:
  - Версионный контроль промптов (git) + регистр инвариантной версии (hash/версия на каждый вызов).
  - Структура: template + переменные (placeholders) + default, отдельно от исполняемого кода.
  - Метаданные: номера версий, дата, автор, связанная модель, назначенные тесты.
  - Системы: PromptLayer, basic CMS, LangSmith, флэт-файлы + CI.
  - Изменение не сразу у всех: canary/feature flag для конкретной версии промпта.
  - Логирование: всегда сохранять версию промпта, которая использовалась для данного ответа.
- Частые ошибки: править промпт прямо в коде каждый раз; нет истории изменений.
- Красные флаги: «промпт меняется, а логи игнорируют версию», «нет регрессионных тестов промпта».

### 20. What is model versioning, and how do you handle model rollbacks?
- Идеал: каждая версия модели (веса, токены, конфиг) имеет ID и метаданные; деплой старой версии при регрессии.
- Обязательные пункты:
  - Registry: MLflow/model registry или репозиторий, хранить веса/артефакты + метаданные (дата, датасет, метрики).
  - Иммутабельность: каждый артефакт версии неизменяем.
  - Деплой: тег версии в serving (например vLLM с конкретным checkpoint).
  - Rollback: при деградации метрик (latency/качество) — переключить роутинг на старую версию; автоматический rollback по алерту.
  - Сочетается с canary: постепенный вывод новой версии.
  - Аудиты: лог, какая версия использовалась для какого отработавшего запроса.
- Частые ошибки: перезаписывать артефакт (или удалять старые); нет автоматического отката.
- Красные флаги: «модель одна», «не храним веса/чекпоинты».

### 21. How do you implement rate limiting and throttling for LLM APIs?
- Идеал: ограничение числа запросов/токенов в минуту/час на user/tenant; избыток может быть отклонён или поставлен в очередь.
- Обязательные пункты:
  - Механизм: token bucket, fixed window, sliding window — на уровне per-user/per-key.
  - Отличие от обычного: стоимость — токены (а не только число запросов) тоже надо ограничивать.
  - Отдают 429 Too Many Requests с Retry-After.
  - Очереди/буферы для не-поточных запросов, но с ограничением.
  - Разворачивается на gateway (Kong/Envoy), API-слой или ingress.
  - Квотирование по план/тир (free tier).
  - Мониторинг очков, алерты при 429.
- Частые ошибки: лимиты только по числу запросов (без токенов); забыть Retry-After.
- Красные флаги: «rate limit = одна бесконечная очередь», «нет контроля переполнения бюджета».

### 22. How do you handle model updates and migrations without downtime?
- Идеал: деплой новой версии без прерывания: синяя/зелёная развёртка/canary, переключение трафика, откат.
- Обязательные пункты:
  - Release: новая версия деплоится отдельным деплойментом, развёртывание новой реплики, горячий swap на роутере.
  - Canary/shadow: процент трафика пускается на новую версию, мониторинг качества → полный rollout.
  - Idempotent launch: модель можно выгружать/загружать без остановки (KV-кеш не персистится — сессии пересоздаются).
  - Перекодировка/миграция формата: input/output schema — back-совместимая; версия промпта и формат вызова.
  - Feature flags/роутинг: переключение централизованно.
  - Мониторинг после миграции + моментальный откат при регрессии.
- Частые ошибки: перезапуск каждого узла сразу, нет промежуточной валидации.
- Красные флаги: «нельзя обновить модель без остановки», «откат только на сервере вручную».

### 23. What is the role of feature flags in AI deployments?
- Идеал: флаги отключают/включают функциональность или определённую версию промпта/модели на нужный процент без нового деплоя.
- Обязательные пункты:
  - Быстрый откат: переключить флаг — откатиться без деплоя.
  - Canary-вывод: процент пользователей на новую модель/промпт.
  - A/B experiment management: включать и выключать вариацию.
  - Что можно флагать: версию модели, версию промпта/модели, конкретную функцию, вкл/выкл агента целиком.
  - Интеграция с мониторингом: при деградации — выключаем флаг.
- Частые ошибки: использовать флаги как постоянную замену управления версиями.
- Красные флаги: «флаги вместо отката», «флаг не имеет канонической стратегии».

### 24. How do you implement logging and tracing for LLM applications?
- Идеал: логи + трассы + метрики с контекстом запросов (inputs, outputs, tool calls, tokens cost).
- Обязательные пункты:
  - Structured logs: поля request_id, model, prompt version, tokens, latency, error.
  - Traces: request flow через tree; spans: LLM call, tool call, RAG retrieval, guardrail.
  - Tracing: OpenTelemetry + специализированный инструменты (LangSmith, Phoenix, Helicone) или ручные телеметрии-обёртки.
  - Отправлять: промпт (возможно вырезать секреты), completion, tool result, kwargs.
  - Никогда не логировать сырые PII/секреты: redact sensitive data.
  - Sampling: каждый десятый — полный трейс, остальные без промпта.
  - Alerts: из трейса строим метрики → алерт.
- Частые ошибки: логировать текст целиком без структуры; не связывать с пользователем.
- Красные флаги: «логи = файл с текстом», «нет trace ID».

### 25. How do you handle PII and sensitive data in LLM inputs and outputs?
- Идеал: PII-защита на всех уровнях: на входе фильтровать, на выходе не давать модели печатать.
- Обязательные пункты:
  - Mask/detection: PII scanner (regex, spaCy, Presidio + LLM) — обнаруживает карты, телефоны, email, имена.
  - Input: перед отправкой заменить реальные данные на placeholders ([masked]) → модель не видит.
  - Output: замена найденных PII на [hidden] перед показом пользователю.
  - Хранение: не писать голые промпты/ответы в логи без редэкшн; key хранить отдельно.
  - Encryption at rest/в transit + контроль доступа; data handling policy.
  - Обучение моделей на чувствительных данных запрещено по умолчанию (data processing agreements).
  - Audit: логировать факт обработки PII без содержимого.
- Частые ошибки: логировать реальные номера карт, пароли; хранить в таблицах.
- Красные флаги: «у нас нет PII», «маскирование не обязательно».

### 26. What is a gateway pattern for LLM API management?
- Идеал: единая точка входа (API gateway) ко всем LLM-провайдерам/моделям; исходящие запросы принимаются одним слоем, унифицируется формат.
- Обязательные пункты:
  - Функции gateway: маршрутизация (какая модель), rate limiting/token, балансировка, retries/fallbacks, кэширование, авторизация.
  - Протокол: унифицированный endpoint (OpenAI-compatible) поверх разных провайдеров.
  - Роутинг по требованиям запроса (cost/latency/модель) — связь с LLM routing.
  - TLS/termination, логирование, A/B, градация нагрузки.
  - Примеры: OpenAI (частично), Kong+LLM plugins, unified proxy-слой
  - Балансировка между моделями одного провайдера: fallback при деградации.
- Частые ошибки: каждая служба напрямую звонит провайдеру; нет центрального управления.
- Красные флаги: «gateway = только прокси», «нет retries/fallback в gateway».

### 27. How does Token Streaming work?
- Идеал: сервер отдаёт токены по мере генерации (а не весь ответ в конце) — SSE, HTTP keep-open, `text/event-stream`.
- Обязательные пункты:
  - Модель генерирует авторегрессивно по одному токену; стриминг — отправка каждого токена client'у сразу.
  - TTFT резко падает; пользователь чувствует отзывчивость.
  - SSE: отправка через `Content-Type: text/event-stream`; каждая часть — `data: <json>` + blank line.
  - Формат данных в реальных системах: JSON (полный объект с token) → каждый `data:` line.
  - Завершение: последним идёт `data: [DONE]` marker → клиент знает конец.
  - SSE однонаправленный (server→client), более простой, чем WebSocket, реконнектится автоматически.
  - Когда не подходит WebSocket: двусторонний чат, где нужен client→server realtime.
- Частые ошибки: ждать весь ответ целиком; путать SSE и WebSocket.
- Красные флаги: «стриминг — это лишь смена восприятия», «[DONE] marker не нужен».
