### 28. How do you implement streaming responses for real-time AI applications?
- Идеал: стримить токены через Server-Sent Events — держать HTTP-соединение открытым, Content-Type `text/event-stream`, каждый токен отдельной строкой `data:`, финальный маркер `[DONE]`.
- Обязательные пункты:
  - Каждое событие — строка `data:` + пустая строка-разделитель; соединение не закрывается, пока не придёт `[DONE]`.
  - Стриминг даёт маленький time-to-first-token: токен отправляется в момент готовности, пользователь сразу видит ответ; важно на длинных генерациях (иначе пустой экран).
- Частые ошибки: ждать весь ответ и слать одним JSON; думать, что streaming ускоряет саму генерацию.
- Красные флаги: «берём WebSockets, потому что это модно»; «[DONE] можно не слать»; «блокируем юзера до конца генерации».

### 29. How does vLLM work?
- Идеал: vLLM — high-throughput движок для serving LLM; ключевые идеи — PagedAttention и continuous batching; всё упирается в эффективное управление KV cache.
- Обязательные пункты:
  - PagedAttention дробит KV cache на блоки фиксированного размера (как страницы ОС), выделяет по требованию, хранит block table — нет over-reservation и фрагментации, разрешено sharing (общий префикс, beam search).
  - Continuous batching на каждом decode-шаге выкидывает завершившиеся запросы и подставляет новые из очереди — GPU не простаивает; есть OpenAI-совместимый API.
- Частые ошибки: путать со статическим батчингом; думать, что узкое место — математика, а не KV-память.
- Красные флаги: «vLLM обучает модели»; «KV cache бесконечна»; «страницы обязаны лежать подряд».

### 30. How does SGLang work?
- Идеал: serving-фреймворк из frontend-языка (Python) + runtime; сердце — RadixAttention, дерево общих префиксов для переиспользования KV cache.
- Обязательные пункты:
  - RadixAttention хранит KV cache в radix-дереве: общий префикс (system prompt, документ) считается один раз и разделяется запросами; при нехватке памяти вытесняет LRU.
  - Фронтенд-язык (`@sglang.function` + `gen`) описывает многошаговые вызовы, runtime исполняет и структурирует генерацию (structured output, constrained decoding).
- Частые ошибки: считать SGLang просто «vLLM v2»; игнорировать то, что фреймворк реально исполняет вызовы, а не только стримит.
- Красные флаги: «SGLang дообучает модели»; «префиксы пересчитываются для каждого запроса».

### 31. How does TensorRT-LLM work?
- Идеал: NVIDIA-библиотека для максимальной скорости инференса на NVIDIA GPU; заранее (build-time) компилирует модель в engine, потом только исполняет.
- Обязательные пункты:
  - Build: ahead-of-time оптимизация — kernel fusion, kernel auto-tuning, quantization; результат — engine, привязанный к конкретной GPU/точности/размерам (recompile при смене).
  - Runtime: paged KV cache, in-flight batching, CUDA graphs, speculative decoding; подходит для предельно низкой латентности.
- Частые ошибки: думать о TensorRT-LLM как о «просто vLLM от NVIDIA»; ждать, что engine переносится на любой GPU.
- Красные флаги: «compiles every request at runtime»; «один engine под любую GPU»; «работает без NVIDIA GPU».

### 32. How does llama.cpp run LLMs on everyday hardware?
- Идеал: llama.cpp — C/C++ инференс-движок, который локально на обычном железе запускает LLM за счёт квантизации, GGUF и mmap.
- Обязательные пункты:
  - Квантизация по блокам со scale-фактором (например Q4_K_M — super-block 256 весов, K-quant) уменьшает вес 7B примерно с 14 GB до ~4 GB с небольшой потерей качества.
  - GGUF — один файл: веса + архитектура + токенизатор + quant settings; mmap грузит только нужные страницы и разрешает sharing; `gpu-layers` делит модель между CPU и GPU.
- Частые ошибки: считать, что квантизация бесплатна; думать, что GPU обязателен.
- Красные флаги: «Q4_K_M = 4 бита для всего, меньше не бывает»; «GGUF это просто веса»; «llama.cpp работает только на Mac».

### 33. How does Ollama work?
- Идеал: Ollama — простой локальный раннер поверх llama.cpp/GGML: скачивает квантизованную GGUF-модель, запускает процесс сервера (порт 11434) и отдаёт ответы.
- Обязательные пункты:
  - `ollama run` = client (CLI/API) → server: если модели нет — `pull`, затем load в память, chat template, tokenizer, stream токенов; `keep_alive` держит модель в памяти.
  - Modelfile описывает кастом: FROM (база), PARAMETER (temperature, num_ctx), SYSTEM; слои хранятся по hash — общие слои дедуплицируются (экономия диск).
- Частые ошибки: думать, что Ollama обучает/дообучает; путать Ollama с vLLM-сервером для прода.
- Красные флаги: «ollama run сразу обучает модель»; «Modelfile это формат модели в облаке»; «без GPU не работает».

### 34. When would you choose vLLM vs SGLang vs TensorRT-LLM?
- Идеал: vLLM — универсальный дефолт (простой, OpenAI-совместимый API, широкий парк моделей); SGLang — когда много общих префиксов/повторяющихся system-промптов и нужен structured output; TensorRT-LLM — когда критична предельная скорость и можно потратить время на build.
- Обязательные пункты:
  - vLLM: PagedAttention + continuous batching = высокая пропускная способность при минимуме настройки.
  - SGLang: RadixAttention-дерево общих префиксов и frontend-язык для многошаговых/структурированных программ.
  - TensorRT-LLM: ahead-of-time build + kernel auto-tuning на конкретном GPU, самый низкий пинг у NVIDIA, но engine привязан к железу.
- Частые ошибки: выбирать по хайпу, а не по нагрузке; игнорировать паттерн запросов (одинаковые префиксы → SGLang/vLLM cache).
- Красные флаги: «все три взаимозаменяемы»; «TensorRT-LLM даёт профит без build-time».

### 35. What are the key SLAs and metrics for production AI systems (latency, throughput, availability)?
- Идеал: SLA формулируют через измеримые SLO: латентность (TTFT + межтокеновый интервал, tail p95/p99), throughput (токены/с, requests/s), availability (аптайм %) и quality-метрики.
- Обязательные пункты:
  - Latency: TTFT (первый токен) и TPOT/inter-token latency; цель обычно p95/p99, а не среднее.
  - Throughput: tokens/sec и requests/sec (считай и по режимам — prefill vs decode); availability ~99.9%+; плюс error rate, cost per token, KV-cache hit rate.
  - SLA = бизнес-цель (например p99 < 2 c, аптайм 99.9%) + error budget для релизов.
- Частые ошибки: мерить только среднюю латентность; путать SLA (контракт) с SLO (целевые значения).
- Красные флаги: «99.9% аптайм без бэкла если нет бэклап»; «между p95 и p99 разницы нет».

### 36. Cloud vs on-device Model Deployment for AI applications.
- Идеал: деплой — где живёт модель. Cloud: «данные идут к модели» — мощная модель, мгновенные апдейты, но латентность сети, зависимость от интернета, per-request cost. On-device: «модель идёт к данным» — приватность, ноль round-trip, работает офлайн, но модель маленькая и апдейты раскатываются медленно.
- Обязательные пункты:
  - Cloud: путь phone→server→phone (round trip ~50–200 мс), данные уходят с устройства, обновление модели — один релиз для всех, стоит за каждый запрос вечно.
  - On-device: нужен интернет? offline → on-device; глубоко личные данные → on-device; гибрид: маленькая модель локально решает простое, облако — сложное.
- Частые ошибки: игнорировать round-trip и политику данных; думать, что on-device всегда лучше для скорости.
- Красные флаги: «on-device всегда дешевле»; «cloud всегда «лучше»»; «на устройстве модель всегда того же качества, что frontier».

### 37. How do you implement fallback strategies when the primary model is unavailable or rate-limited?
- Идеал: многоступенчатая схема: primary → next (другой провайдер/дешёвая модель) → безопасный дефолт (кешированный/шаблонный ответ), плюс retry с backoff, circuit breaker, таймауты/rate-limit detection.
- Обязательные пункты:
  - Ретраи: ограниченные, с экспоненциальным backoff и jitter — на 429/5xx/network; не ретраить идемпотентные операции бездумно.
  - Circuit breaker: после N ошибок отключать primary на время, не слать к нему запросы; feature flag / роутер выбирает бэкап мгновенно.
  - Деградация нелинейно: fallback на семантический кеш, на более простую модель, на жёсткий ответ «переформулируйте позже».
- Частые ошибки: бесконечные ретраи; нет breaker → каскадный фейл.
- Красные флаги: «бэкап не нужен, провайдер на 100% надёжен»; «ретраим как попало без jitter».

### 38. How do you implement structured output from LLMs reliably in production?
- Идеал: функция не исполняется моделью — модель возвращает JSON-вызов (name + arguments) по описаниям (JSON schema); исполняет наш код, результат возвращается модели, и она пишет финальный ответ.
- Обязательные пункты:
  - Описать функции: name + description + parameters (JSON schema); conversation loop: user → model (JSON call) → наш код выполняет → tool result → final answer.
  - Для JSON-режима/structured output: constrained decoding (grammar) или json_schema + промпт, валидация на стороне кода, ретрай при невалидном JSON.
- Частые ошибки: парсить «сырой» вывод регулярками; думать, что модель сама выполняет функцию.
- Красные флаги: «просто попроси «ответь в JSON» и всё» — без схемы и валидации; «невалидный JSON — это нормально».

### 39. How do you handle long contexts efficiently in production (context compression, prefix caching)?
- Идеал: два инструмента — prompt/prefix caching (переиспользуем KV cache повторяющегося префикса) и context compaction (сжимаем старое в пересказ вместо выбрасывания).
- Обязательные пункты:
  - Prefix caching: длинные статичные префиксы (system instructions, документы) в начале промпта — точное совпадение токенов, KV cache читается повторно; ставь статичное до переменной части.
  - Контекстная компакция: при переполнении окна старые сообщения суммируются (LLM) в конспект — факты сохраняются; sliding window просто режет старое и теряет факты.
- Частые ошибки: префикс должен быть буквально тем же; компактить префикс (стабильные инструкции) — их лучше кэшировать, а не пересказывать.
- Красные флаги: «удаляй старые сообщения при переполнении»; «сжимаем всё, включая system prompt с семантикой».

### 40. What is semantic routing, and how do you implement it in a multi-model system?
- Идеал: semantic routing — выбор модели по смыслу запроса (эмбеддинг/классификатор), в отличие от хард-рул; цель — держать качество при низких cost/latency: простые → дешёвые, сложные → frontier.
- Обязательные пункты:
  - Методы: rule-based (ключевые слова, длина), classifier-based (обученный на (query, best-model)), embedding-based (query-эмбеддинг → ближайший reference), LLM-as-router (маленький LLM выбирает).
  - Роутер должен быть очень быстрым — его латентность < ~10% латентности выбранной модели; пример экономии: $15/1M output у frontier vs $0.5 у small → 30x.
- Частые ошибки: роутить по одному ключевому слову (хрупко); игнорировать то, что роутер сам по себe — дополнительный вызов LLM.
- Красные флаги: «все запросы на самую умную модель, так надёжнее»; «роутер — лишний источник ошибок».
