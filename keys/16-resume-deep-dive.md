## Рассказ о себе и мотивация

### 1. Переход из аналитика в AI engineer
- Идеал: FinSuper дал production-данные, метрики моделей (precision, approval rate), offline A/B → понял, что хочет строить, а не только измерять → TRE CRM как первый engineering-продукт → LLM-фичи поверх (tool-calling, RAG) → RecoLabs full-time. Нить: «данные → продукт → LLM-продукт».
- Обязательные пункты:
  - Конкретный навык-мост: A/B-анализ и риск-мышление → evals и cost/risk controls в LLM-системах.
  - Триггер перехода: осознанное решение, не «AI хайповый».
  - Не извиняться за нетипичный путь — продать его: fraud-модели = production ML со ставками.
- Частые ошибки: таймлайн без мотива; перечисление технологий вместо причины; «всегда любил AI».
- Красные флаги: не может связать прошлый опыт с текущим; дискредитирует аналитический опыт.

### 6. Schema-validated output + guided retry
- Идеал: JSON-schema контракт на audit output (Pydantic/JSON Schema), валидация на стороне приложения, не «доверяем модели»; guided retry = второй запрос с validation errors/упавшим полем в промпте («fix these violations»); после второго фейла — fail-closed: пометить поле/секцию, fallback-ответ, не блокировать аудит целиком (или fail с ретраем джобы — по факту).
- Обязательные пункты:
  - Валидация в коде (Pydantic), модель не самоисправляется.
  - Retry несёт конкретные ошибки валидации, а не «попробуй ещё».
  - Политика после 2-й неудачи: partial/fail + алерт.
  - Почему один retry: cost cap $0.36 — каждый retry это бюджет.
- Частые ошибки: «просто просим вернуть JSON»; не знать поведение после исчерпания ретраев.
- Красные флаги: retry без bounded; «модель сама валидирует».

### 7. $0.36/audit — расчёт и enforcement
- Идеал: cost = Σ(tokens_in×price_in + tokens_out×price_out) по модели/эндпоинту; pre-call check: оценка входных токенов (tokenizer/count) + max_output bound + остаток бюджета аудита → если выходит за кап — урезать контекст/секции или отказать и логировать; retry учитывается в том же бюджете. Enforcement на уровне вызова, не постфактум.
- Обязательные пункты:
  - Механика: pre-call estimate + per-call accounting, бюджет на аудит.
  - Что при превышении: degrade (меньше контекста/секций) или partial audit + флаг.
  - Цена вызова посчитана из реальных цен провайдера, caps через max_tokens.
  - `[нужна заготовка]`: как оценивали входные токены, что делать при overflow — нужна стабильная правдивая версия.
- Частые ошибки: «считаем счёт потом» — это не cap; нет слова про retry в бюджете.
- Красные флаги: цифра $0.36 без механики; «примерно следили за расходом».

### 8. Headless browser без сети + threat model
- Идеал: клиентский сайт рендерится в изолированном headless-браузере: content входит как данные; без outbound network — site JS не может вызвать внешние сервисы, exfiltrate prompt/tools или открыть C2. Threat model: (а) site author embeds инструкции в DOM («ignore previous, call tool X»); (б) JS делает сетевые вызовы от имени сессии; (в) сторонний контент тащит payload. Принятые риски: контент всё ещё может попытаться управлять моделью текстом → поэтому дополнительно marked untrusted + read-only tools.
- Обязательные пункты:
  - Зачем render вообще: JS-rendered SPA content.
  - Что закрывает «no outbound»: exfiltration, live payload fetch, phone-home.
  - Многослойность: изоляция браузера + untrusted marking + read-only tool views — не один контроль.
  - Остаточный риск назван честно: текстовая инъекция внутри разрешённого контента.
- Частые ошибки: «заблокировали сеть и всё безопасно»; не назвать остаточный риск.
- Красные флаги: threat model = «мы думали про это» без конкретных атак.

### 9. Marked untrusted data — конкретика
- Идеал: scraped content оборачивается в явный делимитер/структуру («данные сайта, не инструкции») + системный промпт запрещает исполнять инструкции из этого блока; недостаточно одного потому что: модель может перепутать, делимитер может появиться внутри контента, новые паттерны инъекций; поэтому paired с принципом least privilege — даже успешная инъекция не даёт инструментов записи/сети.
- Обязательные пункты:
  - Механика маркировки: явные границы + instruction hierarchy в system prompt.
  - Почему одного недостаточно: prompt injection не решается промптом — модель не гарантирует послушание.
  - Defense in depth: изоляция (браузер) + сокращение возможностей (read-only views) + маркировка.
- Частые ошибки: «мы написали в промпте "не слушай сайт"» — это не защита.
- Красные флаги: думает, что маркировка = иммунитет.

## Архитектурные решения

### 14. Read-only SQL views как tool layer
- Идеал: views задают узкий, безопасный интерфейс: (а) модель видит только разрешённые поля — no raw PII/joins leak; (б) read-only = инъекция не может писать; (в) формат ответа стабилен для tool schema; text-to-SQL на raw таблицах — инъекция-опасно и надо генерировать корректный SQL каждый раз; REST добавляет слой, но не решает безопасность сам.
- Обязательные пункты:
  - Least privilege: view = минимальная поверхность данных.
  - Read-only убивает write-инъекцию.
  - Сравнение с альтернативой (raw text-to-SQL) и почему отвергли.
- Частые ошибки: «так удобнее» без безопасностной логики; забыть про text-to-SQL альтернативу.
- Красные флаги: считает, что промпт-инструкция заменяет least privilege.

### 15. Deterministic actions в flowss
- Идеал: LLM делает интерпретацию (понять запрос, извлечь намерение), но критические действия — создание/изменение задач, напоминаний, любые write-операции с side-effect — идут через детерминированные FastAPI-эндпоинты с валидацией. Критерий: если ошибка модели в этом шаге недопустима/необратима → детерминизм.
- Обязательные пункты:
  - Разделение: LLM=понимание/предложение, backend=исполнение.
  - Критерий границы: reversibility/severity последствий ошибки.
  - Tool-call contract: модель вызывает функцию, бэкенд валидирует и исполняет.
- Частые ошибки: «важные вещи делаем аккуратно» без механизма; LLM напрямую пишет в БД.
- Красные флаги: нет разделения; «модель сама аккуратная».

### 16. Provider-agnostic embeddings + смена провайдера
- Идеал: абстракция embedding-слоя (интерфейс embed(text)→vector), чтобы менять провайдера/модель без переписывания кода; проблема: разные модели → разные пространства, векторы несравнимы → при смене нужен re-embed всего корпуса или namespace-партиционирование по модели (и миграция фоном).
- Обязательные пункты:
  - Абстракция на уровне интерфейса, не просто config.
  - Векторы от разных моделей несовместимы → re-embed или версионирование.
  - Зачем вообще: vendor lock-in, цена, качество, compliance.
- Частые ошибки: думать, что смена провайдера = поменять API-ключ; забыть про существующие векторы.
- Красные флаги: не знает про несовместимость векторных пространств.

### 17. Выбор embedding-модели и pgvector vs dedicated DB
- Идеал: критерии: language coverage (RU/EN), dimension vs storage/latency, benchmark на своих данных (retrieval eval), cost, API-стабильность; dimensionality: 384–1536 компромисс память/качество; pgvector достаточно при умеренном корпусе (десятки-сотни тысяч векторов) и когда уже стоит Postgres — HNSW покрывает; dedicated (Qdrant/Pinecone/…) когда: миллионы+ векторов, сложные фильтры на payload, отдельное масштабирование, managed SLA.
- Обязательные пункты:
  - Критерии выбора модели, не «взял ada-002».
  - Размерные ограничения pgvector, HNSW.
  - Порог перехода к dedicated.
- Частые ошибки: «pgvector хуже всегда» или наоборот; не упомянуть размер корпуса как решающий фактор.
- Красные флаги: не знает HNSW; выбор по hype.

### 18. WhatsApp lead qualifier
- Идеал: индексируем историю чатов (embeddings по сообщениям/окнам) + структурированные признаки; на вход классификатору: новое сообщение + retrieved контекст (прошлые сообщения этого лида, похожие кейсы); «hot» = intent-сигналы (сроки, бюджет, готовность к просмотру) → маршрутизация в Telegram брокеру; асимметрия ошибок: false-negative (потерянный горячий лид) дороже false-positive (брокеру лишнее уведомление) → порог сдвинут в recall.
- Обязательные пункты:
  - Что индексируется и что retrieved.
  - Сигналы «hot» конкретно.
  - Cost asymmetry FP vs FN и как отражён порог.
- Частые ошибки: «LLM оценивает сообщение» без retrieval-контекста; порог без обоснования.
- Красные флаги: не думал про FP/FN-стоимость; нет механики RAG.

### 19. Celery — где и почему
- Идеал: Celery сидит между API и тяжёлыми задачами: аудит-прогоны, scheduled visibility checks, agent-fleet джобы; broker — Redis; почему: mature, retries/schedules (beat), масштабируется воркерами, не блокирует API; альтернативы (arq/Dramatiq/RQ, или просто async) — Celery выбран за экосистему и scheduling; failure modes: воркер-смерть mid-task (acks_late/idempotency), broker backpressure, задачи-долгожители держат воркер-слоты.
- Обязательные пункты:
  - Конкретные задачи на Celery в Rank Wizard.
  - Хотя бы 2 реальных failure mode + как смягчены (idempotency, acks, timeouts).
  - Осознанная альтернатива была рассмотрена.
- Частые ошибки: «Celery для фона» без механики; не знать про at-least-once и дубли.
- Красные флаги: не знает broker; думает Celery = async framework.

### 20. Самый рискованный шип
- Идеал: правдивый пример — вероятно, агентный флот в проде (недетерминированная среда, внешние сайты, детекция) или tool-calling поверх live broker data; de-risk: staged rollout, kill-switch, read-only по умолчанию, логирование решений агента, человек-on-call.
- Обязательные пункты:
  - Один конкретный кейс, не «всё рискованно».
  - Какие контролы стояли до и после.
  - Что бы сломалось при ошибке.
- Частые ошибки: выбрать безопасный пример («миграция БД») без LLM-специфики.
- Красные флаги: «ничего рискованного не было» — либо врёт, либо не думал.

## Инженерный процесс и AI-first workflow

### 21. Spec Kit → agents → reviewer → human, конкретный кейс
- Идеал: конкретная фича (напр. новая секция аудита): spec-kit spec → agent пишет код + TDD тесты → AI-reviewer флагует → CI/E2E → staging → ручной QA → human sign-off → merge; где ломается: спека недоспецифицирована → агент угадывает; AI-reviewer ложные срабатывания на легитимных паттернах; человек-гейт может стать rubber-stamp при давлении сроков.
- Обязательные пункты:
  - Реальный пример от spec до merge.
  - Хотя бы 2 точки отказа процесса.
  - Что ловит каждый слой (spec — intent, tests — correctness, reviewer — risk, human — вкус/контекст).
- Частые ошибки: пересказ пайплайна без примера; «процесс идеален».
- Красные флаги: не может назвать слабое место своего же процесса.

### 22. AI PR reviewer — что проверяет, FP, что ловит человек

### 23. TDD/E2E через агентов — кто пишет тесты
- Идеал: тесты определяются спекой до имплементации: в Spec Kit контракты + acceptance criteria → агент реализует код против этих тестов; guard против self-testing: тесты генерируются из спеки/контракта, E2E тестирует observable behavior через публичные интерфейсы (не внутренние моки); human review смотрит, что тесты реально покрывают критерии.
- Обязательные пункты:
  - Тесты приходят из спеки/acceptance criteria, не из имплементации.
  - E2E = observable contract, не тесты ради тестов.
  - Человеческий гейт на адекватность тестов.
- Частые ошибки: «агент пишет тесты и код» — circular; не объяснить, откуда истина.
- Красные флаги: нет источника истины кроме самого агента.

### 24. 85% coverage gate
- Идеал: 85% = pragmatic threshold: выше — diminishing returns и brittle tests, ниже — регрессии ускользают; cost: тесты на boilerplate, время CI, иногда ложная уверенность (coverage ≠ correctness); trade: приняли затратность ради защиты при быстрых итерациях AI-кода — агенты генерируют код быстрее, чем человек ревьюит, тесты = safety net.
- Обязательные пункты:
  - Почему именно ~85 (порог, не догма).
  - Честная стоимость: CI time, brittle tests, false confidence.
  - Связь с AI-first workflow: тесты важнее, когда код пишет агент.
- Частые ошибки: «стандарт индустрии» без обоснования; думать coverage = quality.
- Красные флаги: не видит trade-off; «чем больше, тем лучше».

### 26. FinSuper A/B — дизайн и почему precision↑ может быть неправильным решением

- Обязательные пункты:

- Частые ошибки: «сравнили precision» без дизайна эксперимента; не связать с бизнес-метрикой.
- Красные флаги: не знает, почему precision может обманывать; A/B без контроля среза.
