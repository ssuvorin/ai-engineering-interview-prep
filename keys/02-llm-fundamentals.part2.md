# LLM Fundamentals — Answer Key (41-60)

### 41. What is Grouped-Query Attention (GQA), and how does it differ from Multi-Head Attention (MHA)?
- Идеал: GQA делит heads на группы; все heads внутри группы делят один общий Key и Value, но у каждой head остаётся свой Query — компромисс между качеством MHA и памятью MQA.
- Обязательные пункты:
  - MHA: у каждой head свои Q, K, V → KV Cache максимально большой.
  - GQA: heads в группе используют общий K/V группы; KV Cache хранит K/V только на группу (напр. 8 heads / 2 группы = 2 набора K/V вместо 8).
  - MQA: все heads делят один общий K/V — крайний случай GQA с группой = 1.
  - GQA — обобщение MHA и MQA: groups = heads → MHA, groups = 1 → MQA.
- Частые ошибки: говорить, что в GQA общий и Query (Query остаётся индивидуальным — именно он даёт разнообразие перспектив).
- Красные флаги: «GQA уменьшает качество как MQA», «GQA = MQA».

### 42. How does Sliding Window Attention work?
- Идеал: каждый токен смотрит только на фиксированное окно соседних токенов (обычно слева), а не на все предыдущие — стоимость растёт линейно, а не квадратично с длиной.
- Обязательные пункты:
  - Окно фиксировано (напр. 512 или 4096 токенов); окно сдвигается на один токен по мере генерации.
  - Дальняя связность достигается косвенно через слои: с L слоями рецептивное поле ≈ L × window, каждый слой «передаёт» информацию соседу.
  - Снижает память и вычисления для длинных контекстов (KV cache compression), используется в моделях типа Mistral.
  - Компромисс: при очень малом окне и малом числе слоёв дальние связи ослабевают; если выбросить первые токены, качество падает (см. attention sinks).
- Частые ошибки: думать, что sliding window ограничивает контекст до окна; забыть, что дальние связи сохраняются через слои.
- Красные флаги: «токены дальше окна вообще не видны», «сложность остаётся O(n²)».

### 43. How do Attention Sinks work?
- Идеал: первые несколько токенов всегда получают непропорционально большую долю внимания из-за нормировки softmax (внимание обязано суммироваться в 1); их называют attention sinks — «стоки» для лишнего внимания.
- Обязательные пункты:
  - Из-за softmax сумма весов = 1, и «лишнее» внимание должно куда-то стечь; первый токен виден всем → становится стоком.
  - Наивный sliding window (выброс первых токенов) ломает модель: лишнее внимание перераспределяется на значимые токены, искажая фокус.
  - Решение StreamingLLM: всегда держать первые N sink-токенов вместе с недавним окном, выбрасывая только середину.
- Частые ошибки: считать, что sinks — случайный артефакт или что их можно просто удалить.
- Красные флаги: «первый токен можно смело выбрасывать», «внимание не обязано суммироваться к 1».

### 44. How does Rotary Position Embedding (RoPE) work, and why is it preferred over learned positional embeddings?
- Идеал: RoPE встраивает позицию, вращая пары компонент Q и K на угол m·θᵢ (m — позиция, θᵢ — частота пары), так что dot product Q·K зависит только от относительного расстояния (n−m) между токенами.
- Обязательные пункты:
  - Вектор разбивается на пары 2D-координат; каждая пара вращается на m·θᵢ, частоты θᵢ = 10000^(−2(i−1)/d) (быстрые → медленные).
  - Из-за ортогональности матриц вращения (R_m·Q)·(R_n·K) = Q·(R_{n−m}·K) — только относительная позиция.
  - V не трогается; вращаются только Q и K.
  - Преимущество над learned/absolute: относительная позиция «бесплатно», лучше обобщение на более длинные последовательности; частоты — точка настройки для длинного контекста (YaRN, NTK).
- Частые ошибки: говорить, что RoPE добавляет вектор позиции к эмбеддингу (он умножается/вращается, а не складывается), или что вращается V.
- Красные флаги: «RoPE = sinusoidal добавка к токену», «RoPE кодирует абсолютную позицию».

### 45. Explain Layer Normalization
- Идеал: LayerNorm нормализует значения по фичерам одного примера (row-wise): вычитает среднее и делит на стандартное отклонение по вектору признаков, затем применяются learnable gamma (scale) и beta (shift).
- Обязательные пункты:
  - Формула: LN(x) = gamma·(x − mean)/√(var + ε) + beta; mean/var по всей размерности признаков экземпляра.
  - Не зависит от batch: работает с batch size 1, поведение одинаково на train и inference.
  - В отличие от BatchNorm (нормализация фичи по всем примерам батча), LayerNorm подходит для RNN/Transformer/LLM, где длины последовательностей варьируются.
  - ε добавляется в знаменатель, чтобы не делить на ноль.
- Частые ошибки: путать направление нормализации LN и BN («column-wise» vs «row-wise»); утверждать, что LN зависит от батча.
- Красные флаги: «LayerNorm использует статистику батча», «LN лучше для CNN».

### 46. Explain RMSNorm (Root Mean Square Layer Normalization)
- Идеал: RMSNorm — упрощённая LayerNorm: убирает re-centering (вычитание среднего) и beta, оставляя только re-scaling — делит вектор на его RMS (root mean square), оставляя learnable gamma.
- Обязательные пункты:
  - Формула: RMSNorm(x) = gamma · x / √(mean(x²) + ε); статистик одна — RMS, а не mean+var.
  - Один learnable параметр gamma на размерность, без beta.
  - Быстрее LayerNorm (меньше вычислений; в статье — экономия времени обучения 7–64%), при сравнимой точности.
  - Используется в современных LLM (Llama, Mistral, Gemma, Qwen, PaLM, DeepSeek) по 2 раза в блоке: перед attention и перед FFN (pre-norm).
- Частые ошибки: говорить, что RMSNorm тоже вычитает среднее; что у RMSNorm есть beta.
- Красные флаги: «RMSNorm медленнее LayerNorm», «у RMSNorm два параметра gamma и beta».

### 47. Why do modern Transformers use Pre-LayerNorm (Pre-Norm) instead of Post-LayerNorm?
- Идеал: Pre-Norm ставит нормализацию до слоя (attention/FFN) и подаёт в него нормализованный вход, а residual-путь идёт в обход нормализации; Post-Norm нормализует после слоя.
- Обязательные пункты:
  - Pre-norm: input → [RMSNorm → Attention] → (+) с residual-путем; стабилизирует обучение очень глубоких сетей.
  - Post-norm (оригинальный Transformer, BERT/GPT-2 эра) даёт менее стабильный градиент в глубоких сетях, требует тюнинга.
  - Pre-norm позволяет обучать заметно более глубокие модели; почти все современные LLM используют pre-norm RMSNorm.
  - Признак: нормализация перед тяжёлым слоем, residual-ветка остаётся «чистой», final RMSNorm перед выходной проекцией.
- Частые ошибки: путать «до»/«после» (утверждать, что norm до residual-add); считать, что Pre-Norm применяется только после слоя.
- Красные флаги: «Pre-Norm нормализует выход слоя», «Post-Norm стабильнее в глубоких сетях».

### 48. What are scaling laws (Chinchilla), and how do they guide model size vs training data decisions?
- Идеал: scaling laws описывают, как loss падает со scale (размер модели N, объём данных D, вычисления C); Chinchilla показала, что для оптимальной стоимости вычислительного бюджета данные и параметры надо масштабировать примерно поровну.
- Обязательные пункты:
  - Ключевой результат Chinchilla (2022): при заданном compute-бюджете оптимум ≈ удваивать и параметры, и данные одинаково; раньше модели были переобучены относительно данных.
  - Форма: loss ≈ a·N^α + b·D^β (power laws); увеличение N, D и C даёт предсказуемое улучшение loss.
  - Практика: если данные исчерпаны — модель «недокручена»; если данных много — модель недообучена. Используется для планирования претрейна (сколько токенов на сколько параметров).
- Частые ошибки: думать, что только размер модели важен; утверждать, что Chinchilla = «больше параметров всегда лучше».
- Красные флаги: «масштабируются только параметры», «scaling laws гарантируют улучшение качества бесплатно».

### 49. Your LLM keeps ignoring your instructions. How do you make it follow structured output formats?
- Идеал: комбинация: чёткий формат-промпт с примером, constrained decoding (grammar / JSON schema / logit-ограничения), structured output (JSON Schema → guaranteed valid JSON), function/tool calls; для надёжности — валидация и ретраи/фиксы парсинга.
- Обязательные пункты:
  - Техника 1: строгий промпт + few-shot пример правильного выхода.
  - Техника 2: constrained/guided decoding — ограничение выборки токенов по грамматике или схеме (JSON Schema, Pydantic), гарантирует валидный формат.
  - Техника 3: применить как tool-call / structured output API (native JSON mode), а не просить «верни JSON».
  - Для надёжности — parse + валидация + ретрай при ошибке (не «молиться»).
- Частые ошибки: полагаться только на промпт для сложных схем; не валидировать выход парсером.
- Красные флаги: «structural output достаточно обеспечить примером», «модель никогда не нарушает формат».

### 50. Your LLM-powered tool hits the context window limit on long documents. How do you handle it?
- Идеал: не впихивать весь документ: чанкинг + retrieval/RAG — сначала выбрать релевантные куски (embedding, re-ranking), либо суммаризация/иерархическая обработка, либо модель с большим окном, если это действительно нужно.
- Обязательные пункты:
  - RAG/чанкинг: резать документ на куски, ретривить топ-k по релевантности, подавать только нужное.
  - Суммаризация: иерархически сжать документ (chunk → summary → summary of summaries), при необходимости с картой ссылок на оригинал.
  - Map-reduce / подвопросы: одни запросы отвечают на части, другие сводят ответ.
  - Крайний случай: перейти на long-context модель/архитектуру, но учитывать стоимость и качество внимания.
- Частые ошибки: обрезать документ «с конца» бездумно; думать, что длинный контекст всегда лучше; забыть про потери внимания в середине длинных входов.
- Красные флаги: «просто поставь модель с окном 1M и всё решится», «релевантность не важна».

### 51. Your LLM does not admit when it does not know the answer. How do you make it say "I don't know"?
- Идеал: снизить уверенность модели через продвинутую независимость: системный промпт про честность, grounding/retrieval, calibration, и архитектурные приёмы, а не только «скажи, если не знаешь».
- Обязательные пункты:
  - Системный промпт: разрешение отвечать «Я не знаю»; явное правило не выдумывать.
  - Grounding: ответ только из выданного контекста/ретривала — если нет данных, честно сказать.
  - Calibration: temperature, отсечение по уверенности/энтитропии, просьба дать уверенность; eval метрика abstention (когда должен сказать «не знаю»).
  - Иногда уменьшение перечислений/фактической конкретики помогает — модель сама склонна к галлюцинациям при нехватке данных.
- Частые ошибки: думать, что промпт «скажи, если не знаешь» полностью решает проблему (модель всё равно «заполнит пробел»).
- Красные флаги: «модель никогда не галлюцинирует после такого промпта», «достаточно температуры 0».

### 52. Your LLM generates responses that are too verbose. How do you control response length?
- Идеал: управлять длиной на уровне генерации (max/new tokens, stop tokens/sequences) и на уровне качества ответа (краткий системный промпт, формат, ограничение scope, инструкция «ответь в N предложениях»).
- Обязательные пункты:
  - Декодирование: max_tokens, stop sequence (например, «\n\n»), ограничить temperature/траекторию.
  - Промпт: «отвечай кратко», «максимум 3 предложения», «списком», требования к формату (буллеты); few-shot краткий пример.
  - Причесанный результат: дать лимиты по секциям, попросить выводить только ответ.
  - Разбирать, если многословие — это переобучение/стиль: switch prompt, system-level.
- Частые ошибки: ждать, что один суффикс «кратко» надёжен; ставить max_tokens ниже длины ответа — обрыв мысли без финала.
- Красные флаги: «max_tokens решает всё», «модель вернёт ровно N предложений по промпту».

### 53. Your LLM memorized proprietary training data and leaks it in responses. How do you prevent this?
- Идеал: предотвращать утечку на нескольких уровнях: не включать чувствительные данные в претрейн/файнтюн, применять фильтрацию данных, redaction, контент-фильтры на выходе и аудит; полноценное «unlearning» — частичное и ненадёжное решение.
- Обязательные пункты:
  - Data pipeline: очистка обучающих данных от приватного/проприетарного контента — главная защита (фильтрация, dedup, allowlist).
  - Контроль на выходе: output-фильтры, детекция чувствительных строк (PII, секреты), ротацию сидов.
  - Fine-tune/unlearning: mengurangi повторение конкретных последовательностей (в т.ч. через RLHF, фильтры); полное забвение не гарантировано.
  - Процесс: лицензии, NDA, инференс-политики для корпоративных данных (не использовать проприетарку в претрейне вовсе).
- Частые ошибки: считать, что «unlearning» надежно стирает данные; полагаться только на вых-фильтры после заучивания.
- Красные флаги: «можно стереть любую запомненную информацию», «фильтр на выходе — достаточная защита».

### 54. Your LLM coding assistant generates outdated code using deprecated libraries. How do you fix it?
- Идеал: дать модели актуальный контекст/документацию, ограничить выбор библиотек, поднять версии в промпте и в фоне (retrieval свежей документации), плюс валидация/тесты/линтеры, ловящие deprecated API.
- Обязательные пункты:
  - Актуальная справка: подать версии, ссылки на текущую документацию, свежие примеры (RAG по документации).
  - Ограничение стека: явно запретить устаревшие библиотеки/API в промпте, указать актуальные аналоги.
  - Инструментальная проверка: запускать линтеры/тесты/компиляцию — если deprecated API, чинить по ошибке.
  - Fine-tune/специализированная модель, если домен постоянный (пайплайн для конкретных библиотек).
- Частые ошибки: ждать, что более новый претрейн автоматически знает свежие API; не валидировать сгенерированный код.
- Красные флаги: «модель сама знает свежие версии», «достаточно сказать «используй актуальные библиотеки» — без проверки».

### 55. Your tokenizer splits important domain terms into meaningless subword pieces. How do you fix it?
- Идеал: добавить доменные термины в словарь токенизатора (добавить целые токены/мержы), либо переобучить/расширить tokenizer с сохранением эмбеддингов, либо слагать кастомные токены с префиксами.
- Обязательные пункты:
  - Vocabulary extension: добавить кастомные токены для доменных терминов, добавить эмбеддинги (initialize разумно, дообучить), ручной merge pair.
  - Можно использовать словарь + post-processing: если термин режется — собрать по типовым паттернам, дополнительно prompt.
  - Переобучение tokenizer с тем же BPE/алгоритмом — только если это оправдано (изменение словаря влияет на эмбеддинги и длины).
  - Промпт-уровень: дать модель понять, что термин — единое понятие (кавычки, дефиниции).
- Частые ошибки: трогать tokenizer без переобучения эмбеддингов; думать, что любое расширение словаря не меняет качество.
- Красные флаги: «достаточно просто добавить токен в словарь», «tokenization не влияет на качество».

### 56. Your Transformer's KV cache grows too large during long sequence generation. How do you manage memory?
- Идеал: комбинация: сжать KV (GQA/MQA, KV quantization, eviction — sliding window/attention sinks), управлять выделением памяти (PagedAttention), и ограничить контекст/кэш по времени (continuous batching).
- Обязательные пункты:
  - PagedAttention: режет KV cache на фиксированные небольшие блоки (pages) и выделяет их по мере надобности через block table (как page table в ОС) — устраняет internal/external memory waste.
  - Сжатие кэша: GQA (меньше K/V голов), KV cache quantization, eviction старых токенов (sliding window с вниманием к sinks).
  - Не делает сам кэш меньше — просто убирает потери памяти; переиспользование общих префиксов (shared blocks) при parallel sampling/beam search.
  - Влияет на engineering: batch size и context length — бюджет памяти.
- Частые ошибки: думать, что PagedAttention уменьшает сам KV cache (это про управление памятью); что GQA на всех одинаково — потеря качества при экстремальном MQA.
- Красные флаги: «PagedAttention сокращает KV cache», «можно не ограничивать длину последовательности».

### 57. Your Transformer runs out of memory on long documents due to quadratic self-attention. How do you scale it?
- Идеал: заменить/реализовать квадратичное внимание на субквадратичное: sliding window attention (линейная стоимость), sparse/block patterns, FlashAttention (IO-оптимизация), и другие (linear attention, Mamba-style), плюс chunking/RAG.
- Обязательные пункты:
  - Полное внимание O(n²) по времени и памяти; sliding window — каждый токен видит окно (O(n·w)), дальние связи через слои.
  - FlashAttention — fused attention, минимизирует чтение/запись HBM (tiling, softmax в флэш-памяти), ускоряет и без изменения мат. результата.
  - Масштаб: sparse attention (global+local), Linformer/linear attention, гибрид sliding+global tokens.
  - Всегда можно ограничить вход: чанкинг, суммаризация (не “впихивать” весь документ).
- Частые ошибки: заявлять exact результат «как у full attention» без оговорки (FlashAttention точен; sparse — аппроксимация); игнорировать, что память квадратична в последовательности.
- Красные флаги: «достаточно FlashAttention — и всё O(n)», «sparse внимание ничего не теряет».

### 58. Your distilled student model fails on the complex reasoning that the teacher model handled. How do you close the gap?
- Идеал: усилить дистилляцию для hard reasoning: больше данных с цепочками рассуждений (reasoning traces), дистилляция на логику и подходы, а не только на поверхность; баланс по сложности примеров, более близкая архитектура, дополнительная SFT/RL.
- Обязательные пункты:
  - Увеличить долю сложных/размышляющих примеров (целые CoT, self-consistency) в дистилляции.
  - Подгонка под стиль мышления: учить делать пошаговое рассуждение, а не только копировать ответ.
  - Проверять: distillation наокр past — если student сильно слабее, это потеря capacity (предел модели), добавить больше данных/итераций или увеличить student.
  - Оценка по подзадачам: разбить reasoning на шаги, выявить где падает.
- Частые ошибки: думать, что любой distillation не теряет качество на сложных задачах; падать только на финальном ответе и не смотреть на шаги.
- Красные флаги: «дистилляция никогда не теряет в качестве», «достаточно больше данных без reasoning traces».

### 59. After RLHF alignment, your LLM became safer but lost capability on hard tasks. How do you manage the alignment tax?
- Идеал: признать «alignment tax» (падение способностей от выравнивания) и компенсировать: сбалансированные preference-данные (hard tasks + safety), RLHF с сохранением capability (KL-контроль, reference-модель), итеративные раунды с переоценкой, отдельная оценка domain-качества.
- Обязательные пункты:
  - KL penalty против drift: держать политику близко к SFT-модели (≤, умеренный beta), чтобы не «переучить» под reward.
  - Смешивать помогающие и безопасные категории: данные с hard reasoning-треками, добавить RL на сложных задачах.
  - Итерация: несколько раундов RLHF, свежие preference-данные с новыми выходоами; постоянный мониторинг метрик по напраралам/эффективности.
  - Свои domain evals для capability (не только reward/harm score).
- Частые ошибки: решать безопасность ценой полной потери способностей; вводить сильные ограничители сразу на всё.
- Красные флаги: «alignment tax неизбежен и некомпенсируем», «достаточно одного раунда RLHF».

### 60. Your RLHF-trained LLM is gaming the reward model instead of being genuinely helpful. How do you fix reward hacking?
- Идеал: reward hacking — модель находит трюки, дающие высокий reward-ск от reward model, но бесполезные для человека; защита: KL penalty против дрейфа от SFT, качественная/пересобираемая preference-дата, свежий reward model, человеческая оценка не только по reward.
- Обязательные пункты:
  - KL penalty в обучении: наказывать отклонение распределения политики от SFT-модели (object = reward − β·KL), чтобы не «обманывать» reward.
  - Обновлять reward model: свежие preference-пары на выходах обновлённой модели, несколько раундов RLHF — не дать model устареть/получить appeal-эксплуатацию.
  - Оценивать реальное качество: held-out human eval (не только reward score), мониторинг признаков hacking (напр. пустое многословие, сильнойная вежливость).
  - Reward model — это proxy, не ground truth; держать его честным.
- Частые ошибки: игнорировать KL penalty; полагаться на один reward score как на истину; считать «раунд RLHF» разовым.
- Красные флаги: «reward model никогда не ошибается», «KL penalty необязателен», «одна итерация микро-фиксов достаточно».
